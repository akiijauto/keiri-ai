1. 目的と適用範囲

個人情報・機密情報を含む紙資料をスマートフォン／タブレットで読み取り、 OCR処理から確認までを端末内で完結させたうえで、 人間が確認した項目だけを所定のWebサイトへ入力する仕組みを構築する。

本システムの対象業務は「お客様が記入した書類の内容を、業務Webシステムへ登録する」作業である。 書類の撮影・読み取り・確認は端末内で行い、登録のためにWebサイトへ入力する段階でのみ通信を許可する。

1.1 適用範囲外

  • 読み取ったデータを自社サーバへ集約・蓄積すること（本システムは中継も蓄積も行わない）
  • 登録の完全自動化（送信ボタンは常に人間が押す）
  • 本リポジトリ内の別企画（請求書仕訳AI）との機能連携。両者は独立しており、コードもデータも共有しない

2. 最重要原則

機能要件よりセキュリティ要件を優先する。以下は設計上の不変条件であり、 利便性を理由に緩めない。

ID原則実装上の担保
原則1個人情報を外部OCRへ送信しないOCRはML Kit（モデル同梱）／Vision（端末内強制）のみ。外部OCR SDKを依存に含めない
原則2個人情報を生成AIへ送信しない生成AIのSDK・APIクライアントを一切依存に含めない
原則3OCRは端末内で完結させるAndroid: 同梱モデル／iOS: requiresOnDeviceRecognition = true

原則7個人情報をログへ記録しない監査ログは値を検査し、個人情報らしき文字列を拒否（INV-5）

原則10セキュリティ要件を機能要件より優先する本書および脅威モデルで判断基準を明示

3. 業務要件

3.1 業務フロー

紙資料（お客様の記入済み書類）
   │
   ├─ 取込元A: OCRアプリ（Android / iPhone / iPad）
   │     撮影 → 画像補正 → 端末内OCR → 項目抽出 → 人間の確認・修正
   │
   └─ 取込元B: 入居フォーム等のWeb入力
         直接入力 → 同じ正規化・検証 → 人間の確認
                     │
                     ▼
          確認済みデータ（SLO Handoff Envelope）
                     │
                     ▼
          登録先の業務Webサイト
          検証 → 入力欄へ充填 → 人間が内容を確認 → 人間が送信

3.2 対象項目

Profile jp.personal.basic/1 として定義する。正規化・検証規則は取込元と登録先で共通とする。

name氏名全角、姓名間は全角スペース1個1〜64文字、数字を含まない
name_kanaフリガナ全角カタカナ全角カタカナと全角スペースのみ
birthday生年月日YYYY-MM-DD実在日付、1900-01-01〜本日
postal_code郵便番号NNN-NNNN数字7桁
address住所全角（数字とハイフンは半角）1〜128文字
phone電話番号数字のみ先頭0、10桁または11桁
emailメールアドレス半角小文字形式検査、254文字以下
customer_no顧客番号半角大文字英数とハイフン、1〜32文字
move_in_date入居予定日YYYY-MM-DD実在日付

3.3 帳票種別と必須項目

document_type用途必須項目

5. 受け渡しプロトコル要件

取込元が変わっても登録先が変わらずに済むよう、受け渡しの契約を1つに定める。 詳細は protocol/SPEC.md、機械可読な定義は protocol/slo-handoff-v1.schema.json。

5.1 不変条件

ID不変条件
INV-1人間が確認した項目だけがEnvelopeに載る
INV-2Envelopeに原画像・OCR生テキスト全文を含めない
INV-3失効時刻を過ぎたEnvelopeは無条件に破棄する
INV-4登録先は入力欄を埋めるところまで。自動送信しない
INV-5監査ログに項目値を書かない
INV-6正規化・検証は取込元と登録先の双方で実行し、一致しなければ拒否する

5.2 受け渡し手段

ID手段Level通信完全性検証
T1画面表示（人間が転記）1不要不要
T2項目ごとのコピー2不要不要
T3アプリ内WebViewへの充填3–4登録先のみHMAC-SHA256 必須
T4ループバック（127.0.0.1）3–4端末内のみHMAC-SHA256 必須

5.3 Web入力元との連携

入居フォーム等でWeb入力された内容も、source.kind = "web-form" として 同一のEnvelopeに載せる。登録先は取込元を意識せず、受け口を1つ実装すればよい。 正規化規則・検証手順・監査ログの経路はOCR由来と完全に共通とする。

7. セキュリティ要件

ID要件実装状態
S-01OCRフェーズで外部通信を行わないofflineフレーバーはINTERNET権限なし実装・検証済
S-02外部OCR API・生成AI APIを使用しない依存に含めない実装済
S-03解析SDK・広告SDK・外部ログ収集を組み込まない依存に含めない実装済

S-06スクリーンショット・画面録画を抑止するAndroid: FLAG_SECURE ／ iOS: 部分的iOSは限定的
S-07クラウドバックアップ・端末間転送を禁止するdataExtractionRules / isExcludedFromBackup実装済
S-08原画像をOCR後に破棄するメモリ上のみ、直後にrecycle実装済
S-09クリップボードの利用を制限する機微フラグ付与／iOSは有効期限60秒・端末内限定実装済
S-10通信先を許可リストに限定するnetworkSecurityConfig／ATS／ブリッジのオリジン検証実装済
S-11監査ログに個人情報を記録しない属性キーと値を実行時検査実装・検証済
S-12Root化／Jailbreak端末での利用を抑止する簡易検出＋MDM運用簡易検出のみ
S-13引き渡しの改ざん・リプレイを検知するHMAC＋nonce＋失効＋handoff_id重複拒否実装・検証済
S-06 の限界について。 iOSにはAndroidのFLAG_SECUREに相当する、スクリーンショットを禁止するAPIが存在しない。 アプリ側でできるのはアプリスイッチャーでの内容秘匿までである。 実運用では管理対象端末（MDM）側の制限と併用することを前提とする。 「アプリだけで防げる」と誤解しないよう、ここに明記する。

10. Web連携要件

  • 登録先サイトは slo-bridge.js を読み込むだけで受け口が成立すること
  • 項目とフォーム入力欄の対応は、サイトごとのマッピング定義ファイルで管理すること
  • マッピングが無い項目は自動推定してよいが、推定で埋めた欄は画面上で区別すること
  • 登録先の表記（YYYY/MM/DD、郵便番号2分割、電話番号3分割など）への変換はブリッジ側で行うこと
  • 許可リスト外のオリジンからの引き渡しは、理由を返さずに破棄すること

12. 運用要件

  • 実運用では個人所有端末ではなく業務専用端末を使用する
  • MDMにより、クラウド同期・USB転送・スクリーンショット・外部共有を制御する
  • 監査ログは端末内に保持し、値を含まないことを前提に持ち出し可能とする
  • 撮影画像・OCR結果・pcapなど個人情報を含み得るデータはリポジトリへ保存しない
  • テストデータはすべて架空データとする
