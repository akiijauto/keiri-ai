課題1: 通信権限が、宣言していないのに混入していた

何が起きたか

OCR専用の offline フレーバーは「INTERNET権限を持たない」ことを設計の柱にしていました。 マニフェストに <uses-permission android:name="android.permission.INTERNET"/> を 書かなければ済むはずでした。ビルドしたAPKを実測すると、こうなっていました。 

$ aapt2 dump permissions app-offline-debug.apk
package: jp.slo.android.offline
uses-permission: name='android.permission.CAMERA'
uses-permission: name='android.permission.USE_BIOMETRIC'
uses-permission: name='android.permission.ACCESS_NETWORK_STATE'
uses-permission: name='android.permission.INTERNET'      <-- 持っている

原因

Androidのマニフェストマージャは、依存ライブラリのマニフェストを自動的に取り込みます。 ML Kit が依存する Google Play services 系のライブラリが INTERNET と ACCESS_NETWORK_STATE を宣言しており、 それがアプリのマニフェストへ合流していました。 「書かなければ付かない」は誤りでした。

解決

フレーバー側のマニフェストで明示的に取り除きます。

<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">
    <uses-permission android:name="android.permission.INTERNET" tools:node="remove" />
    <uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" tools:node="remove" />
</manifest>

再発防止

Gradleタスク :app:verifyOfflineFlavorHasNoInternet を追加し、 生成されたAPKそのものを毎回 aapt2 で検査して、 権限があればビルドを失敗させるようにしました。

学び

セキュリティの主張は、ソースコードではなく成果物に対して検証する。 「そう書いたつもり」と「そうなっている」は別物で、今回はまさに食い違っていた。 この1件だけで、原則8（実測して検証する）を仕組みにした価値があった。

課題2: 検証タスクが、古いAPKを見て「合格」と言いかけた

何が起きたか

課題1の修正後、gradle :app:assembleOfflineDebug :app:verifyOfflineFlavorHasNoInternet を実行したところ、修正が効いているはずなのに失敗しました。 マージ後のマニフェストを確認すると INTERNET は消えていました。

原因

検証タスクに dependsOn を書いていなかったため、 Gradleがタスクの実行順を保証せず、前回ビルドの古いAPKを検査していました。 今回はたまたま「誤って不合格」でしたが、順序が逆なら 「修正前のAPKを検査して合格と言う」ことも起こり得ました。そちらの方が危険です。

解決

val verifyOfflineFlavorHasNoInternet by tasks.registering {
    // 検証対象は「実際にパッケージされたAPK」。必ず先にビルドさせる。
    dependsOn("assembleOfflineDebug")
    ...
}

学び

検証タスクは、検証対象の生成に必ず依存させる。 そうでない検証は、静かに古い証跡を承認してしまう。

課題3: CSPを厳しくしたら、自分のページが動かなくなった

何が起きたか

登録先サイトのブラウザE2Eで、6件中4件が失敗しました。 エラーは Cannot read properties of undefined (reading '_deliver')。 つまり window.SLO が生えていない。

原因

許可リスト方式の実例として、開発サーバに script-src 'self' を含むCSPを付けていました。 一方でページ側は <script type="module">...</script> と インラインで書いていたため、CSPが正しく仕事をしてブロックしていました。 同様に style="margin-top:14px" というインラインstyle属性も style-src 'self' に弾かれていました。

解決

ページのスクリプトを app.js として外部ファイル化し、インラインstyleはクラスに置き換えました。 'unsafe-inline' を足してCSPを緩める選択はしていません。 緩めれば、この仕組みが守ろうとしているものが減ります。

再発防止

E2Eテストに「CSPヘッダが default-src 'self' と connect-src 'self' を 含むこと」を確認する項目を入れました。CSPが緩められたら、テストが落ちます。

学び

セキュリティ設定でテストが落ちたとき、最初に疑うべきは設定ではなく実装のほう。 「テストを通すために設定を緩める」を1回でも許すと、あとは坂道になる。 登録先サイトに組み込む側も同じ壁に当たるので、READMEに明記した。

課題4: 3言語で同じ結果を出すのは、思ったより難しい

何が起きたか

正規化規則を Kotlin・JavaScript・Swift の3つで実装する設計にしました。 ここでずれると、取込元が「正しい」と判断した値を登録先が「不正」と拒否します。 机上のレビューではずれを見つけられません。

具体的にずれやすかった点

論点ずれの内容対処
数値の文字列表現 1.0 を Kotlin は "1.0"、JavaScript は "1" と書く。 HMACの対象文字列が変わるので署名が一致しない 正準化の規則で「整数値は小数点なし」と固定し、3実装に同じ関数を置いた
キーの並び順 言語ごとの既定のソートが必ずしもUTF-16コードユニット順ではない 比較関数を自前で実装し、ベクタで検証
閏年・和暦 標準の日付ライブラリはタイムゾーンやロケールの影響を受ける 日付型を自前で持ち、閏年判定と和暦換算を3実装で同じコードにした
全角スペースの扱い 「空白文字」の定義が言語ごとに違う（U+3000を含むか） 対象文字を明示列挙し、正規表現の \s に頼らない

解決

protocol/testdata/ に共通テストベクタを置き、3実装すべてがこれを読むようにしました。 さらに正準化/HMACのベクタは第4の実装（Python）で生成しています。 3実装が同じ勘違いを共有していても、Python生成のベクタとは合いません。

学び

「同じ仕様で実装する」だけでは同じにならない。同じ入力に対する同じ出力を、 実行可能な形で共有して初めて揃う。 ベクタが落ちたら、ベクタではなく実装を直す。この順序を守れるかがすべて。

課題5: 和暦とOCR誤読補正の適用順序

何が起きたか

OCRは数字を読み違えます。0をO、1をI、 5をSと読むことがよくあるので、 数字が期待される場所ではこれを補正します。

ところが日付には和暦があります。S55.1.1（昭和55年1月1日）に 素直に補正をかけると 555.1.1 になり、日付として読めなくなります。 H（平成）R（令和）M（明治）T（大正）も同様の危険があります。

解決

順序を決めました。まず和暦として解釈を試み、失敗した場合に限って数字補正をかける。 

ERA_RE.find(raw)?.let { ... }          // 先に和暦を試す
val fixed = Text.fixOcrDigits(raw)     // 読めなかったときだけ補正
WESTERN_RE.find(fixed)?.let { ... }

ベクタには S55.1.1 → 1980-01-01 と 198O/O1/O1 → 1980-01-01 の両方を入れ、 どちらかを壊す変更をしたらテストが落ちるようにしました。

学び

「賢い補正」は、別の正しい入力を壊す。補正には必ず適用範囲を決め、 その境界をテストで固定する。氏名や住所に数字補正をかけないのも同じ理由。

課題6: Kotlinのブロックコメントは入れ子になる

何が起きたか

テストのドキュメントコメントに protocol/testdata/*.json と書いたところ、 Syntax error: Unclosed comment でコンパイルが落ちました。エラー位置はファイル末尾で、 原因箇所を指していません。

原因

Kotlinのブロックコメントは入れ子を許します。コメント内の /*（testdata/* の部分）が 新しいコメントの開始と解釈され、閉じ括弧が1つ足りなくなっていました。 C系言語の感覚だと気づきにくい挙動です。

解決

コメント中のパス表記からワイルドカードを外しました（protocol/testdata 配下）。

学び

「Unclosed comment」がファイル末尾で出たら、コメント内の /* を疑う。 ドキュメントコメントにglobパターンを書かない。

課題7: KotlinのプロパティとメソッドのJVMシグネチャ衝突

何が起きたか

var offlineCapture by mutableStateOf(true)
    private set

fun setOfflineCapture(offline: Boolean) { ... }   // Platform declaration clash

var offlineCapture はJVM上で setOfflineCapture(Z)V を生成するため、 同名のメソッドと衝突しました。

解決

メソッド名を markOfflineCapture に変更。 「setterを private にしつつ、限定された経路でだけ更新させたい」意図も名前で表現できました。

課題8: Composeの weight を import してしまった

androidx.compose.foundation.layout.weight を import したところ Cannot access ... it is internal in file でコンパイルエラー。 weight は RowScope / ColumnScope の拡張なので import 不要でした。 IDEの自動importに任せると、同名の internal 宣言を拾うことがあります。

課題9: OCRの信頼度が端末によっては返らない

ML Kit の Text.Line.confidence は、端末やモデルの版によって値を返しません。 非null前提で書くと落ちる可能性があり、かといって ?. を付けると プラットフォーム型の扱いで警告になります。 

// 返らない場合は 1.0 として扱う。キャストで安全に受ける。
val confidence = (line.confidence as? Float)?.toDouble() ?: 1.0

そのうえで、確認画面は「信頼度 高／中／低」と言葉で表示しています。 数値を出しても人間の判断材料になりにくく、値の欠落に意味を与えすぎるためです。

課題10: E2Eテストが5回に1回落ちた

何が起きたか

全テストを通し直したところ、直前まで安定していた「改ざんEnvelopeの拒否」テストが1回だけ失敗しました。 同じテストを3回続けて流すと3回とも成功します。典型的な不安定テストです。

原因

登録先ページのスクリプトは、マッピング定義を await fetch() で読んでから ブリッジを設置します。テスト側はページを開いた直後に window.SLO._deliver() を呼ぶため、 設置が間に合わないと window.SLO が未定義になります。 失効テストのほうは、直前でEnvelopeへの署名（非同期処理）を待つぶん時間が稼げていて、 たまたま表面化していませんでした。

解決

await page.waitForFunction(() => Boolean(window.SLO));
await page.evaluate(async (envelope) => { await window.SLO._deliver(envelope); }, env);

修正後、5回連続で全件成功することを確認しました。

学び

セキュリティの拒否条件を確かめるテストが不安定なのは、特に危険。 「たまに落ちるやつ」として放置されると、本当に拒否できなくなった日にも 同じ扱いで見過ごされる。落ちた回数が少ないうちに原因を突き止めておく。

なお、この不具合はテスト側だけの問題で、製品コードの動作には影響しません。 ただし「ブリッジの設置は非同期である」という事実は、 登録先サイトへ組み込む側にも影響するため、READMEに書いておくべき性質のものです。

課題11: 実機で電話番号とメールアドレスしか取れなかった

何が起きたか

実機（Androidタブレット）で検証用の帳票を撮影したところ、 電話番号とメールアドレスだけが正しく取得され、他は1項目も取れませんでした。 確認画面には「未確認の必須項目」がずらりと並び、氏名も生年月日も空のままです。

この報告から何が分かったか

取れた2項目は、ラベルを見なくても行全体の形だけで判定できる項目です。 パターン照合（信頼度0.60）の経路だけが生きていて、 ラベル照合の経路が丸ごと死んでいる、と読めます。 つまり「文字が読めていない」のではなく「読めているのにラベルと値が結びついていない」。

原因

帳票は「ラベル列｜値列」の表です。ML Kit はこの表を、 左のラベル列と右の値列を別のブロックとして返すことがあります。 そうなると行の並びは次のようになります。 

氏名
フリガナ
生年月日
…
山田　太郎
ヤマダ　タロウ
昭和55年1月1日
…

抽出処理は「ラベル行に値が無ければ次の行を値とみなす。 ただし次の行もラベルなら諦める」という規則でした。 この並びではすべてのラベルの次の行がまたラベルなので、全項目が諦められます。 残るのはパターン照合だけ——報告された症状とぴたり一致します。

さらに悪いことに、ラベル列の最後の項目（入居予定日）だけは次の行がラベルではないため、 まったく無関係な値（顧客番号 CUS-1024）と結びついていました。 取れないより、間違って結びつくほうが危険です。

推測で直さなかったこと

最初に報告を受けた時点では、原因を「撮影条件」と「抽出規則」のどちらとも決められませんでした。 確認画面には抽出結果しか出ないため、 「読めていない」のか「読めたが結びつかない」のかを区別する手段が無かったのです。 そこで先に、OCRが返した行をそのまま並べるデバッグ画面を足しました。 その上で、報告された症状（2項目だけ取れる）から並び順の仮説を立て、 単体テストで実際に再現してから直しています。 

抽出=move_in_date:, postal_code:150-0001, phone:09012345678, email:taro.yamada@example.co.jp
未取得=[name, name_kana, birthday, address]

解決

OCRエンジンが返す行の外接矩形を抽出処理へ渡し、 並び順ではなく位置でラベルと値を対応づけるようにしました。

  • 同じ行（縦の重なりが半分以上）で、ラベルの右にある最も近いセルを値とする（0.85）
  • 無ければ、同じ列（横の重なりが半分以上）で直下にあるセルを値とする（0.75）
  • 位置が分かっているのに見つからなければ、並び順へは戻らない。 戻ると入居予定日と顧客番号のような誤った結びつきが生まれるため
  • 住所の折り返しも位置で判定する。 左側に何か書かれている行は折り返しではなく次の項目の行とみなす。 ラベル語彙に無い項目（勤務先など）でも効く判定です

外接矩形が取れない端末では従来どおり並び順で対応づけます（動作は変わりません）。 iOS の Vision は正規化座標かつ原点が左下なので、 ピクセル座標・原点左上へ直してから渡しています。

学び

「どの項目が取れなかったか」ではなく「どの項目が取れたか」に情報があった。 取れた2項目がどちらもラベル不要で判定できるものだった、という一点が原因を特定させた。 症状の一覧を眺めるのではなく、症状の境目を見る。
帳票OCRを「行のリスト」として扱ったのが設計の誤りだった。 紙の帳票は二次元のレイアウトであり、意味は位置が持っている。 OCRエンジンが位置を返しているのに捨てていた。

再発防止

この並びを共通ベクタ（extract-07-table-columns）として固定しました。 ベクタは Kotlin と Swift の両実装が読むため、片方だけ直る事故を防げます。 折り返しの判定（extract-08）とラベルが値の上にある帳票（extract-09）も同時に追加しています。

設計判断の記録

なぜ通信の有無を「ビルド構成」で分けたか

「OCR中は通信しない」をコードで守ろうとすると、レビューし続けるしかありません。 権限を持たないビルドを用意すれば、OSが強制します。守り方の強さが違います。 offline / web の2フレーバーにしたのはそのためです。

なぜ外部ライブラリを使わずJSONを自作したか

理由は2つあります。

  • OCRフェーズで動くコードの依存を最小にし、意図しない通信を行うSDKの混入余地を減らすため
  • 正準化の出力を3実装でバイト単位に揃えるには、直列化を自分で制御する必要があったため

課題1で見たとおり、依存は勝手に権限を持ち込みます。依存を1つ減らすことには意味がありました。

なぜ入居フォーム（Web入力）も同じEnvelopeに載せたか

登録先の受け口を1つに保つためです。取込元ごとに受け口を作ると、 検証の抜けが取込元の数だけ増えます。 OCR由来かWeb入力由来かは source.kind と origin の違いだけで、 正規化も検証も監査ログも共通の経路を通ります。

なぜ完全自動送信を実装しないか

OCRは必ず間違えます。間違いを人間が見つけられる場所は、送信ボタンの手前しかありません。 自動送信を1つ足すと、その安全網が丸ごと無くなります。 ブリッジには送信ボタンを押す経路自体を作っていません。

次にやること

  1. 実端末でのOCR精度検証。実際の帳票（架空データで印刷したもの）で、 必須項目が取れるかを確認する。ここで駄目なら項目抽出の規則を見直す
  2. 通信監視の実測。tools/analyze_pcap.py は合成pcapで動作確認済み。 実端末の捕捉結果を通して合格を記録する
  3. 処理速度の計測。撮影からOCR結果表示まで3秒以内という目標の妥当性を確認する
  4. iOS版のビルドとテスト。macOS環境で swift test と実機動作を確認する
  5. 対象Webサイトの調査。実際の入力欄・認証・CDN・CAPTCHAを調べ、 マッピング定義と許可リストを確定する
  6. ML Kitの挙動確認。INTERNET権限が無い状態でOCRが正常に動くことを実機で確認する。 モデルは同梱なので動くはずだが、これは実測すべき前提である

次回の開発で使える知識

  • Androidの権限は、依存ライブラリから勝手に増える。APKを実測して確認する
  • 検証タスクは検証対象の生成に依存させる。さもないと古い証跡を承認する
  • 厳しいCSPを入れるなら、インラインの script と style 属性は最初から使わない
  • 複数言語で同じ判定を行うなら、共通テストベクタを最初に作る。実装より先に作る
  • ベクタは、実装とは独立した第4の手段で生成すると、共通の勘違いを検出できる
  • 文字列の補正処理は、必ず適用範囲を決めて境界をテストで固定する
  • Kotlinのブロックコメントは入れ子になる。コメントに /* を書かない
  • 「実装完了」と「実機検証済み」を混同しない。文書上でも区別して書く
