3.1 共有コアを3言語に持つ理由と代償

OS標準のOCR（ML Kit / Vision）を使うため、単一のクロスプラットフォーム実装にはできません。 一方で判定規則がずれると、取込元が「正しい」とした値を登録先が拒否します。 そこで、業務ロジックだけを3言語で実装し、 同一の入力に対する同一の出力を共通テストベクタで固定しました。

代償は保守コストです。規則を1つ変えるたびに3か所を直す必要があります。 これを受け入れる代わりに、ベクタが落ちることで「直し忘れ」が必ず表面化します。

5.1 なぜ受け取り側でも正規化を再計算するのか

HMACは「途中で書き換えられていないこと」を示しますが、 「そもそも取込元が正しい値を作ったか」は示しません。 受け取り側で正規化をやり直し、結果が届いた値と一致しなければ拒否します（INV-6）。 これにより、取込元と登録先で共有コアの版が食い違った場合にも、 黙って通るのではなく明確に落ちます。

7. 項目抽出の仕組み

機械学習ではなく、決定的なルールベース処理です。端末内で完結し、結果を再現できます。

  1. ラベル照合。各行から見出し語（「氏名」「〒」「TEL」など）を探す。 行内で最も左、同着なら最も長いものを採用する（「メールアドレス」が「メール」に負けない）
  2. 値の取得。ラベルの直後に値があればそれを使う（信頼度 0.90）。 空なら次の行を使う（0.75）。次の行にもラベルがある場合は諦める
  3. 住所の折り返し。住所だけは、ラベルの無い後続行を最大2行まで連結する
  4. パターン照合。ラベルの無い行が、行全体で郵便番号・電話番号・ メールアドレスの形をしていれば拾う（0.60）。誤検出を避けるため部分一致は使わない
  5. 正規化と検証。取得した文字列をProfileの規則にかける。 失敗した項目は値を空にし、読み取った生の文字列を「要修正」として人間に見せる

信頼度は 基準値 × OCRの行信頼度 です。 0.80未満は確認画面で警告します。数値そのものは出さず「高／中／低」で示します。

8. 意図的に採用しなかった選択肢

選択肢不採用の理由
クラウドOCR（精度は高い）原則1に反する。本システムの前提が崩れる
生成AIによる項目抽出（柔軟）原則2に反する。ルールベースで足りる範囲に絞った
Flutter / React Native による単一実装OS標準の端末内OCRを使うため、結局OS固有実装が必要。 共有するのは業務ロジックだけにした
JSONライブラリの利用依存を減らすため。加えて正準化を3実装で完全一致させる必要があった
確認済みデータの自社サーバ経由での中継個人情報の保管場所が増える。端末から登録先へ直接渡す
完全自動送信誤りを人間が捕まえる最後の場所を失う
